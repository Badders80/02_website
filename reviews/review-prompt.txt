# Marketplace & MyStable — PRD

## Goal

Two pages that turn site visitors into token holders and give holders a dashboard to track their investments and communications.

## Data Flow (Hybrid Static & Dynamic)

```
[STATIC SYNC (SSOT)]
SSOT_Build/data/horses/*.json     → horses.json (pedigree, metadata)
SSOT_Build/data/trainers/*.json   → trainers.json (rich biography)
SSOT_Build/data/owners/*.json     → owners.json (contact info)
      │
      │  python3 scripts/sync_inventory.py
      ▼
src/data/*.json (local static data) ──► Builds static SEO-friendly pages

[DYNAMIC DATABASE (Google Sheets API)]
1. Inventory Sheet       ──► Live shares sold, listing status, active prices (runtime fetch)
2. Holdings Sheet        ──► Logs dynamic customer holdings & e-signed PDF Drive URLs
3. Leads Sheet           ──► Logs interest forms, waitlists, and manual KYC capture
4. Communications Sheet  ──► Logs outbound email history for MyStable Inbox feed

[BACKEND PIPELINE]
Stripe Checkout Success ──► Serverless webhook stamps e-Sign PDS/SA PDFs
                                ├──► Uploads signed PDFs to Google Drive
                                └──► Writes records to Holdings, Leads, and Communications Sheets
```

* **Hybrid Model**: Structural data (pedigrees, biography) is baked statically from SSOT at build time. Transactional data (available inventory, waitlists, purchases, email history) is updated in real time via Google Sheets API.
* **No Database Middleware**: Google Sheets serves as the secure system of record for v1.

## Status System (Built)

Four lifecycle states shown as badges on marketplace cards and detail pages.

| Badge | When | Grid | Detail page | Buy flow |
|---|---|---|---|---|
| Coming Soon | `listing_status: draft` | Teaser card — name, image, no price | Minimal info. CTA: "Register Interest" | None |
| Become An Owner | `listing_status: active`, shares available | Full card — image, name, trainer, % subscribed | Full detail. CTA: "View Investment Terms" → Modal → "Acquire" | Active |
| Fully Subscribed | `shares_sold >= shares_total` | Greyed card — "Fully Subscribed" badge | Full detail. CTA: "Join Waitlist" | None |
| Term Completed | `listing_status: retired` | Archive card — "Term Completed" badge | Read-only archive | None |

### Status logic
```
if listing_status == "retired" → Term Completed
else if shares_sold >= shares_total → Fully Subscribed
else if listing_status == "active" && shares_available > 0 → Become An Owner
else if listing_status == "draft" → Coming Soon
```

### Display (Built)
- Marketplace card: "0% subscribed" / "100% subscribed" (not raw unit counts)
- Detail page: same — % subscribed
- Purchase flow: "X% of the horse" (not "total stake")
- No progress bar. 0% = Coming Soon, 100% = Fully Subscribed.

## 2. PRD vs. Addendum Reconciliation

### 2.1 Gatekeeping & Access (RESOLVED)

**Master PRD says:** Details page is fully public for SEO. Right column action panel is "blurred/hidden for guest" with a "Sign In" CTA that preserves context and redirects back.

**Addendum Section 1 originally said:** Detail page is auth-gated. Guests redirected to login before viewing ANY detail.

**Locked decision (user-confirmed):** Go with the **PRD approach** — public details page for SEO, blurred action panel for guests. The addendum's full auth-gating is overridden.

**Gap to fix:** The detail page (`page.tsx`) is currently a **server component** (SSG). It has NO client-side auth state awareness. The right column renders fully for everyone. To implement the blur overlay, we need to either:
- (A) Add a client wrapper component around the right column that checks `useAuth()` and renders a blurred overlay + sign-in CTA when unauthenticated, OR
- (B) Convert the entire detail page to a client component (loses SSG/SEO benefits — NOT recommended).

**Recommended approach:** (A) — Extract the right column into a client component (`ActionPanel.tsx`) that uses `useAuth()`. The left column stays server-rendered for SEO. The right column hydrates client-side and conditionally blurs.

**Context preservation:** The login page already supports `?redirect=/marketplace/[slug]`. The blur overlay CTA just needs to link to `/auth/login?redirect=/marketplace/[slug]`.

**Back navigation:** Breadcrumb already exists in the detail page (`Marketplace / [Horse Name]`). The addendum wants a more prominent `← Back to Marketplace` link — minor UI addition.

### 2.2 KYC Flow (PARTIALLY BUILT — GAPS IN UX)

**What exists:**
- KYC session creation via Stripe Identity (`/api/kyc/create-session`)
- KYC status check via Stripe Identity API (`/api/kyc/status`) — syncs to Firebase custom claims
- Firebase custom claims store `kyc_status: 'verified' | 'pending' | 'none'`
- Auth context exposes `kycStatus` reactively via `onIdTokenChanged`

**What the addendum adds:**
- KYC processing screen at `/marketplace/[id]/kyc-processing` with "Check Status Again" button and fallback lead capture
- KYC fallback: "Can't complete identity verification? Contact support" → writes to Leads sheet

**Answer to Open Question #1 (KYC state storage):** Already answered by the codebase — Firebase Auth custom claims ARE the KYC state store. The `/api/kyc/status` endpoint queries Stripe and syncs to claims. This is the correct architecture. No need for a separate Google Sheet column or pure Stripe query. The processing screen just needs to call `/api/kyc/status` on a button click and check the returned status.

### 2.3 Lead Attribution (NEW — NOT BUILT)

**Addendum proposes:** Client-side UTM/ref capture on landing, persist in localStorage, append to lead/purchase payloads.

**Implementation:**
- New component: `AttributionCapture.tsx` — mounts on all pages, parses URL params on first landing, stores in localStorage
- Utility functions: `getAttribution()` returns stored UTM/ref data
- Integration points: purchase webhook (append UTM to Holdings row), lead forms (append to Leads row)
- The checkout `create-session` route should capture UTM from the request body and pass through to Stripe metadata → webhook reads it

### 2.4 Google Sheets Schema (NEW — PARTIALLY BRIDGED)

**Current state:** The webhook writes Holdings via a Google Apps Script web app URL (`GOOGLE_SHEETS_WEB_APP_URL`). This is a thin bridge — no direct Sheets API integration in the Next.js app.

**Addendum proposes:** 4 tabs (Inventory, Holdings, Leads, Communications) with direct Google Sheets API integration from the Next.js serverless functions.

**Hybrid data model (PRD + Addendum):**
- Structural data (pedigrees, stories, biographies, registry numbers) → SSOT JSON via `sync_inventory.py` at build time
- Transactional data (shares_sold, listing_status, prices, holdings, leads, communications) → Google Sheets API at runtime

**Gap:** No `src/lib/google-sheets.ts` exists. Need to build a Google Sheets client using service account credentials. The existing web app bridge can be replaced or supplemented.

**Risk:** Google Sheets API rate limits on Vercel serverless functions. Need caching strategy (e.g., revalidate every 60s for Inventory reads, immediate writes for Holdings/Leads/Communications).

### 2.5 PDF Generation & Drive Storage (NEW — NOT BUILT)

**Addendum proposes:** On `checkout.session.completed`:
1. Generate signature stamp (date, IP, name, agreement version)
2. Flatten/stamp PDS + SA PDFs via `pdf-lib`
3. Upload to Google Drive via API
4. Get sharing links
5. Save links in Holdings sheet
6. Send welcome email with PDFs attached

**Current webhook:** Only writes a basic holding record to Sheets. No PDF, no Drive, no email.

**Answer to Open Question #2 (PDF template structure):** The existing PDFs at `/public/documents/[slug]/pds.pdf` and `syndicate-agreement.pdf` are flat PDFs (no form fields). The approach should be to **append a signature audit page** to the end of each PDF using `pdf-lib`, containing: signer name, Stripe Identity session ID, verification timestamp, client IP, agreement version, and a legal attestation block. This is more robust than trying to stamp onto existing pages (which risks overlapping content).

**Risk:** `pdf-lib` in a Vercel serverless function — need to verify the bundle size and cold start impact. PDF processing may exceed Vercel's function timeout on cold starts. Alternative: use a separate serverless function or edge function for PDF processing.

### 2.6 MyStable Expansions (NEW)

**Current MyStable:** Reads from `holdings.json` (static). Shows holdings list, onboarding tracker, stable logs feed (mock data only).

**Addendum adds:**
1. **Investor Inbox tab** — queries Communications sheet, filtered by user email, displays email history
2. **Documents section** — queries Holdings sheet for `signed_pds_url` and `signed_sa_url`, filterable by horse

**Gap:** MyStable needs to switch from static JSON to runtime Google Sheets API reads for holdings/communications. This is a significant architectural shift — the page must become dynamic (or use ISR with revalidation).

**Risk:** Converting MyStable from static to dynamic may impact performance. Consider client-side fetching with loading states rather than SSR to maintain snappy initial load.

### 2.7 Two-Stage Build Strategy (NEW)

**Stage 1:** Black & white functional wireframes — get all flows working end-to-end with minimal styling.
**Stage 2:** Apply premium brand polish (gradients, glassmorphism, animations).

**Note:** The existing marketplace already has premium styling. The two-stage approach applies to NEW features (attribution, KYC processing screen, Investor Inbox, Documents section, PDF pipeline). Existing pages keep their current styling.

### Component 3: Attribution Engine

**File:** `src/components/AttributionCapture.tsx` (NEW) + `src/lib/attribution.ts` (NEW)

**Behavior:**
- `AttributionCapture.tsx` — client component, mounted in root layout. On mount, checks URL for `utm_source`, `utm_medium`, `utm_campaign`, `ref`. If present, stores in `localStorage` under key `evo_attribution`. Does not overwrite if already set (first-touch attribution model).
- `attribution.ts` — utility functions:
  - `captureAttribution()` — parse URL params, store in localStorage
  - `getAttribution()` — read from localStorage, return `{ utm_source, utm_medium, utm_campaign, ref }` or empty values
  - `clearAttribution()` — optional, clear after purchase

**Integration points:**
- Checkout create-session: client sends UTM in request body → server includes in Stripe metadata → webhook reads and appends to Holdings row
- Lead forms: append UTM to form submission payload
- KYC fallback: append UTM to manual assistance request

### Component 4: Google Sheets Client Library

**Caching:** Inventory reads cached with 60s TTL (revalidate). Writes are immediate.

## 4. Open Questions (Resolved & Remaining)

### Resolved by Codebase Audit

1. **KYC state storage** → Firebase Auth custom claims. Already implemented. The `/api/kyc/status` endpoint syncs Stripe → Firebase. The auth context reads claims reactively. No Google Sheet column needed for KYC state.

2. **PDF template structure** → Append a signature audit page at the end of each PDF using `pdf-lib`. The existing PDFs are flat (no form fields). Appending is more robust than stamping onto existing content.

3. **Gatekeeping approach** → Public details page with blurred action panel (user-confirmed). SEO-friendly. The left column narrative stays server-rendered.

### Remaining

4. **Google Sheets API auth method** — Service account with JSON key in env var? Or continue using the Google Apps Script web app bridge? The service account is more robust and allows reads (web app bridge is write-only for holdings). Recommendation: service account.

5. **Email sending method** — Gmail API with service account (requires domain-wide delegation) vs. nodemailer with SMTP (simpler, less Google-specific). Recommendation: nodemailer with SMTP for v1 simplicity.

6. **PDF processing location** — Inline in Stripe webhook (risk of timeout) vs. separate serverless function (decoupled, more reliable). Recommendation: separate function triggered by webhook, with fallback to manual sync.

7. **MyStable data source** — Pure Google Sheets API (dynamic, always current) vs. hybrid (static JSON with runtime overlay). Recommendation: hybrid. Static JSON for initial render, client-side fetch for real-time data. Maintains snappy load while showing accurate data.

8. **Google Drive folder structure** — Flat folder with `{slug}_{purchase_id}_pds.pdf` naming vs. nested `/{horse_slug}/{purchase_id}/` folders. Recommendation: nested for organization.

## 7. Risk Summary

| Risk | Impact | Mitigation |
|---|---|---|
| Google Sheets API rate limits | Marketplace/MyStable data unavailable | Cache with TTL, fallback to static JSON |
| Vercel function timeout on PDF generation | Webhook fails, holding not recorded | Split: webhook records holding, separate function generates PDFs. Fail-safe try/catch. |
| `pdf-lib` bundle size on Vercel | Cold start degradation | Verify bundle size. If too large, use edge function or external service. |
| Google Drive API auth complexity | PDF upload fails | Service account with Drive scope. Pre-create folders. |
| Gmail API domain-wide delegation | Email sending blocked | Use SMTP/nodemailer as simpler alternative. |
| Detail page hydration mismatch | SEO/content flash | Use `useEffect` for auth check, render blur only after hydration. Server renders full content for SEO. |
| Google Sheets as database scaling | Performance degrades with rows | Acceptable for v1. Plan migration to proper DB for v2. |
